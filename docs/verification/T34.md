# T34 — Concurrency, authorisation and failure handling (evidence)

Recorded 31 October 2026 on the development laptop. Two kinds of evidence:

1. **Deterministic integration tests** (`npm run verify`: 397 server tests, all passing). They pin each rule with controlled timing, injected failures and mutation checks done in earlier tasks.
2. **Real-stack drills**: separately running processes and real outages. Docker stack (API, worker, PostgreSQL 17, Redis 7.4, Mailpit) plus a **second API process started from the host** on :3001 with the same configuration (the Docker API is :3000). The drill tool is [`apps/server/scripts/t34-drills.mjs`](../../apps/server/scripts/t34-drills.mjs); outages were made by stopping or killing containers.

All numbers are from one laptop, one run each. They show behaviour, not production capacity (that is T35).

## 2. Two instances: 13 of 13 drill checks pass

`node scripts/t34-drills.mjs instances` (A = Docker API, B = host process; owners registered on one instance and verified on the other through Mailpit):

1. A session created on B is valid on A.
2. 40 edits alternating A/B, each read on the other instance by the next redirect: 0 stale.
3. A disable on A is a 410 on B immediately.
4. 10 concurrent edits of one version across instances: one 200, nine 412.
5. 8 simultaneous claims of one alias (4 owners × 2 instances): one 201, seven 409.
6. 8 concurrent retries of one Idempotency-Key across instances: all 201, one link id.
7. 14 creations in a minute split across A and B: exactly 10 succeed, 4 are 429.
8. Another owner gets 404 for someone else's link on both instances.
9. Another owner cannot edit it either (404).
10. Owners get 403 from admin endpoints on both instances.
11. A write without the CSRF token is refused (403).
12. A write from another origin is refused even with the token (403).
13. After logout on B, the same cookie is rejected on A (401).

## 3. Outages

**Redis stopped** (both API instances running):

| Request | Result |
|---|---|
| Redirect on A / on B | 302 in 2 ms / 12 ms (redirects read only PostgreSQL) |
| Anything needing a session (`/api/v1/auth/csrf` on A and B) | 503 `SERVICE_UNAVAILABLE` in ~2 ms (fails closed) |
| `/health/ready` | 200: readiness checks PostgreSQL only, so redirect traffic keeps flowing |
| After Redis restarted | A recovered within ~1 s, B ~1.5 s later; no API restart |

Clicks made during the outage are not captured (counted as capture loss; analytics are approximate by design).

**PostgreSQL stopped:**

| Request | Result |
|---|---|
| Redirect on A / on B / from a browser | 503 in ~3 ms, `Retry-After: 2`, `Cache-Control: no-store` (browser gets the "briefly unavailable" page) |
| `/health/ready` | 503 `{"status":"unavailable","checks":{"postgres":"down"}}`; `/health/live` stays 200 |
| Session-only request (`/api/v1/auth/csrf`) | 200 (Redis only) |
| After PostgreSQL restarted | Redirects on A and B back to 302 within ~1 s; readiness `ready`; no API restart |

**Analytics worker:**

| Drill | Result |
|---|---|
| Worker stopped, 500 real clicks, worker started | Total unchanged while stopped (19), 500 waited in the stream; after restart 519: each counted exactly once |
| 12,000 real clicks queued, worker started, **SIGKILL right after its first commit** (6,000 counted, 500 read but unacknowledged) | After restart the abandoned entries were reclaimed: **12,000 of 12,000 counted, none twice**, stream empty, 0 dead letters |

**Overload** (one API instance, database pool 10, wait queue limit 50, wait budget 2 s):

| Burst | Throughput | Statuses | Latency |
|---|---|---|---|
| 4,000 redirects at 50 concurrent | ~1,800 req/s | 4,000 × 302 | p50 25 ms, p95 43 ms, p99 66 ms |
| 4,000 redirects at 400 concurrent | ~2,200 req/s (mostly 503s) | 585 × 302, 3,415 × 503 | p50 49 ms, p95 1.5 s, max 1.7 s |

No 500 responses during either burst (API log), and readiness stayed `ready`. Shedding is bounded by the 2 s budget, as designed.

## 4. Findings

| Finding | Kind | Action |
|---|---|---|
| While shedding, the slowest requests wait almost the full 2 s pool budget before their 503 (p95 1.5 s at 400 concurrent). A single process with a 10-connection pool starts shedding between 50 and 100 concurrent requests. | Capacity, bounded | **Concrete fix planned for T35** (1,000 rps target): measure on the benchmark setup, then tune per-process pool size, the redirect wait budget (fail faster than 2 s for redirects) and the queue limit, and run several API processes. No release without a measured result. |
| Retries with the same Idempotency-Key count toward the creation limit (the limit is checked before the replay). | Behaviour | Acceptable (retries are requests, and a replay never creates a link); recorded in api-contracts. |
| A challenged guest spends two of five hourly attempts per link (T33). | Product question | Open for the owner. |
| `/health/ready` stays `ready` during a Redis outage. | By design | Redirects (the critical path) do not need Redis; sign-in and creation fail closed with 503. Alerting on Redis belongs to T37 monitoring. |

## 5. Reproducing

1. `docker compose up -d`, then start a second API process from the host with the same `.env`, `PORT=3001`, and `localhost` addresses for PostgreSQL (5432), Redis (6380) and Mailpit SMTP (1025).
2. From `apps/server`: `node scripts/t34-drills.mjs instances`, `node scripts/t34-drills.mjs overload 4000 400`, and `node scripts/t34-drills.mjs clicks <code> <count> [concurrency]` around `docker compose stop|start|kill -s KILL worker`, comparing `link_totals` for the link before and after.
3. Outages: `docker compose stop redis` / `stop postgres`, send requests to both instances, then `start` and wait for recovery.

Development rate-limit counters may need clearing between runs (`rate:*` keys in the local Redis).
