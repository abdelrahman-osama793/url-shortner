# T35 — Capacity benchmark (evidence)

Recorded 31 October 2026 on the development laptop. **Target (D15): one million stored links and 1,000 redirects per second.** Proposed thresholds (technical-design §8, engineering proposals, not owner-approved requirements): 15 minutes at 1,000 scheduled redirects/s after warm-up, server-side p95 below 100 ms, unexpected errors below 0.1 %, p95 analytics visibility within 10 s.

**Result: the target is met on this laptop**, in every workload, with large latency headroom. The first limit above the target is the single analytics worker (about 1,200–1,400 clicks/s); see §5.

This is a bounded experiment on one machine. It is not a claim about the free-tier deployment (D07), which will be far smaller and may sleep.

## 1. Setup

| Item | Value |
|---|---|
| Machine | Laptop, AMD Ryzen 7 6800H (8 cores / 16 threads, up to 4.8 GHz, `powersave` governor), 14 GiB RAM, Linux 6.8; desktop applications running |
| Software | Node 22.23, PostgreSQL 17.11 and Redis 7.4.11 in Docker 29.8 (development compose, default settings: `shared_buffers` 128 MB, `max_connections` 100, Redis AOF on) |
| Data | Separate database `shortlist_bench`: 1,000,000 links (90 % owned by 1,000 owners, 10 % guest, 1 % of owned disabled), 302 MB; Redis database 1. Development data untouched |
| API | 2 processes (`node src/api.js`, ports 3101–3102), `DATABASE_POOL_MAX=10` each, shed limit 50 waiting, 2 s pool wait, `LOG_LEVEL=info` (one log line per request, as in production), `NODE_ENV=development` (production refuses to start without a real challenge provider, T37) |
| Worker | 1 process (batch 500, 4 connections) |
| Load generator | Separate process pinned to its own 2 CPUs (`taskset`); servers pinned to the other 14; PostgreSQL and Redis unpinned. Same machine, so the generator and servers share memory bandwidth and the network is loopback |
| Method | Open model: requests sent on a fixed schedule whatever the server does; client latency measured from the *scheduled* time (no coordinated omission). The generator round-robins across API processes like a load balancer. Server-side latency from the API's own per-request log (`durationMs`) |

Codes are chosen uniformly from the million (**broad**: cold rows, the database's worst case) or 90 % from 1,000 popular codes (**hot**). **Mixed** adds a signed-in owner reading analytics (1.6/s) and creating links (about 9/min), the most their rate limits allow.

## 2. Results at the 1,000 rps target

| Workload | Measured | Redirects | Unexpected errors | Server p50 / p95 / p99 / max | Client p50 / p95 / p99 / max | Clicks counted |
|---|---|---|---|---|---|---|
| Broad | 15 min after 1 min warm-up | 900,000 (891,023 × 302, 8,976 × 410) | 0 | 0.8 / 1.2 / 1.5 / 30 ms | 2.6 / 3.7 / 4.1 / 33 ms | 950,424 of 950,424 |
| Hot | 5 min after 1 min warm-up | 300,000 (296,988 × 302, 3,011 × 410) | 0 | 0.7 / 1.1 / 1.4 / 80 ms | 2.6 / 3.7 / 4.0 / 82 ms | 356,374 of 356,374 |
| Mixed | 15 min after 1 min warm-up | 900,000 (891,050 × 302, 8,949 × 410) | 0 | 0.8 / 1.2 / 1.4 / 35 ms | 2.3 / 3.4 / 4.3 / 38 ms | 950,447 of 950,447 |

- **410s are expected**: 1 % of the seeded links are disabled.
- **Mixed side traffic**: 1,440 analytics reads, all 200, p95 6.8 ms. 138 creations: 90 × 201 and 48 × 429. The 429s are the owner's 100-links-per-day limit, so the limiter worked as designed.
- **Generator health**: no request was skipped, and the scheduler was never more than 16 ms late. The generator used about 15 % of one CPU.
- **Client vs server latency**: the gap of about 2 ms is the generator's event loop and loopback networking. The server-side figure is the one compared with the 100 ms proposal.

**Analytics freshness under load** (`scripts/measure-analytics-freshness.mjs` during a 3-minute 1,000 rps broad run, 60 clicks 1 s apart, polling the owner analytics API every 600 ms): p50 0.33 s, p95 0.60 s, max 0.62 s. All 60 were visible within 10 s and the pipeline reported `healthy`. The figures are limited by the 600 ms poll interval.

**Lag and loss.** The stream backlog never exceeded 311 entries, about 0.3 s of traffic. The worker had drained it by the time each run ended, and no click was lost in any target-rate run.

## 3. Where it breaks (30-second steps, broad)

| Setting | Rate | Result |
|---|---|---|
| 1 API process | 1,000 | Passes (60 s): server p95 1.1 ms, the process at 51 % of a CPU |
| 1 API process | 2,000 | Passes: server p95 1.6 ms, client p99 6.6 ms, no errors |
| 1 API process | 3,000 | **Collapses**: CPU-bound event loop, 91 % answered 503 (shed), 4 connection resets, client p999 20 s |
| 4 API processes | 3,000 | Redirects pass (server p95 1.3 ms, no errors), but **18 % of clicks lost** (`queue_full`) |
| 4 API processes | 5,000 | 0.5 % 503s, server p95 9 ms; **56 % of clicks lost** (`queue_full`) |

Every lost click was a `queue_full` drop logged by the API's capture statistics: the stream reached its 50,000-entry cap and new events were refused, by design, so that redirects never wait for analytics. The single worker drained about 1,200–1,400 clicks/s.

## 4. The T34 finding, revisited

T34 found that one process with a 10-connection pool sheds between 50 and 100 *simultaneous* requests, with p95 1.5 s while shedding. That was a closed-loop burst (400 clients waiting on each other). At a realistic arrival rate it does not show: at 1,000/s a redirect takes about 1 ms, so only one or two are in flight at once. The pool is not the limit. **No pool, wait-budget or queue-limit change was needed for the target, so none was made.** The measured per-process limit is CPU, at about 2,000–2,500 redirects/s, and the answer to it is more processes (§3), not a bigger pool.

## 5. Findings

| Finding | Kind | Action |
|---|---|---|
| The 1,000 rps target is met with large margins: server p95 1.2 ms against the proposed 100 ms, zero errors, zero loss, freshness p95 0.6 s against 10 s | Result | None. The thresholds remain proposals until the owner selects them |
| The single analytics worker is the first bottleneck, at about 1,200–1,400 clicks/s (only 20–40 % above the target). Above it, clicks are dropped (bounded, counted, redirects unaffected) | Capacity | Follow-up before any claim above 1,000 rps: bulk inserts or several consumers in the group. Not needed for the target |
| One API process collapses at about 3,000 rps: CPU-bound, mostly 503s, and queued requests can wait seconds because the shed check only sees the pool, not the event loop | Capacity, bounded by deployment | Run at least two processes behind the proxy (T37). Event-loop-delay shedding is an option if a single process must survive overload |
| The run used development settings (`NODE_ENV=development`, default PostgreSQL configuration, Docker on a laptop, the generator on the same machine) | Method limit | Repeat on the chosen hosting (T36–T38) for deployment figures; this report is not one |

## 6. Reproducing

From `apps/server` with Node 22 and the Docker stack running (`docker compose up -d`):

1. `set -a; . ../../.env; set +a; BENCH_OWNER_PASSWORD=<local test password> node scripts/bench/seed.mjs`. This creates and migrates `shortlist_bench` and inserts the million links (about 30 s). To reseed, drop the database first.
2. `BENCH_APIS=2 scripts/bench/run.sh broad 1000 900 60`, then the same with `hot 1000 300 60` and, with `BENCH_OWNER_PASSWORD` set, `mixed 1000 900 60`. Each run starts its own API and worker processes against the benchmark database and stops them afterwards. Results go to `bench-results/<time>-<workload>-<rate>/`, which is git-ignored and holds `report.json` with 5-second samples, `server-latency.json` and the logs.
3. Freshness under load: during a run, `EMAIL=bench-owner-0000@example.test PASSWORD=… API_URL=http://localhost:3101 node scripts/measure-analytics-freshness.mjs 60 1000`.

Rate-limit counters in Redis database 1 may need clearing between mixed runs (`rate:*`).
